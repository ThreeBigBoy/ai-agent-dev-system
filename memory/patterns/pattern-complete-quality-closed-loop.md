# 完整质量闭环流程

## 一句话定义

覆盖从需求分析到功能验收的8步完整质量闭环流程，确保每个阶段都有质量保障、评审留痕和技能映射。

## 问题背景

### 传统工作流的质量缺口

```
┌─────────────────────────────────────────────────────────────┐
│                    传统工作流的质量缺口                        │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  传统流程：                                                   │
│                                                              │
│  PRD 产出 ──→ 技术方案 ──→ 编码实现 ──→ 测试 ──→ 发布          │
│      │          │          │         │                        │
│      ▼          ▼          ▼         ▼                        │
│   缺口1      缺口2       缺口3     缺口4                      │
│                                                              │
│  缺口1: PRD 缺乏系统评审                                       │
│  • 简单打勾或简单会议纪要                                       │
│  • 无详细评审过程、决策逻辑、修改建议                            │
│  • 无法追溯「为什么这样设计」                                    │
│                                                              │
│  缺口2: 技术方案缺乏架构评审                                    │
│  • 直接开始编码，方案质量依赖个人经验                             │
│  • 实现与需求脱节、与架构不符                                    │
│                                                              │
│  缺口3: 实现与方案脱节                                         │
│  • 代码实现与 PRD/技术方案不一致                                  │
│  • 代码评审流于形式，未对照方案                                   │
│                                                              │
│  缺口4: 验收标准模糊                                           │
│  • 无明确验收 Checklist                                         │
│  • 无法对照 specs 验证                                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### AI 工作流的改进需求

```
┌─────────────────────────────────────────────────────────────┐
│                    AI 工作流需要                              │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  需要1: 每个阶段都有明确的质量门禁                              │
│  • 准入条件: 前置阶段完成并通过评审                                │
│  • 准出条件: 产出物符合规范、通过评审、详细留痕                    │
│                                                              │
│  需要2: 每个阶段都有对应的 Skill 映射                          │
│  • 明确哪个 Agent 执行                                         │
│  • 明确触发哪个 Skill                                          │
│  • 明确产出物要求                                               │
│                                                              │
│  需要3: 质量可追溯、可审计                                       │
│  • 评审纪要详细记录评审过程                                       │
│  • 产出物路径规范，易于追溯                                      │
│  • 迭代日志记录执行历史                                          │
│                                                              │
│  需要4: 支持异步协作                                            │
│  • 文档驱动，减少会议                                            │
│  • 评审异步化，书面化留痕                                        │
│  • 支持分布式团队协作                                           │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 模式解决方案

### 核心思想

```
┌─────────────────────────────────────────────────────────────┐
│                  8 步完整质量闭环                             │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│   需求 ──→ PRD ──→ 技术方案 ──→ 编码 ──→ 代码评审 ──→ 验收 ──→ 归档  │
│    │       │         │         │        │         │         │
│    ▼       ▼         ▼         ▼        ▼         ▼         ▼
│  Step1   Step2     Step3     Step4   Step5    Step6    Step7-8
│                                                              │
│  每步都有：                                                    │
│  • 准入条件（前置步骤完成并通过）                               │
│  • 执行方（Agent 角色）                                         │
│  • 触发 Skill                                                  │
│  • 产出物要求                                                  │
│  • 准出条件（评审通过，详细留痕）                                │
│  • 质量门禁（不通过则退回修改）                                  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 8 步详细流程

#### Step 1: 需求分析 (request-analysis)

```yaml
名称: 需求分析
Agent: 产品经理 Agent
触发 Skill: request-analysis

准入条件:
  - 用户提出需求或变更请求
  - 或识别到新的 change-id 需要启动

执行内容:
  - 产出 PRD: design/documents/changes/[change-id]/PRD-[change-id]-[关键词].md
  - 必须符合 8 类内容结构:
    1. 需求来源与背景
    2. 问题价值分析与优先级
    3. 竞品/平台调研
    4. 本迭代目标与成功标准
    5. 产品方案要点
    6. 功能列表与验收标准
    7. 需求验收 Checklist
    8. 与 OpenSpec 的对应关系

产出物:
  - PRD 文档
  - 可选: 市场研究与产品方案.md
  - 可选: 功能需求说明书.md
  - 可选: 需求验收 Checklist.md

准出条件:
  - PRD 文档已产出
  - 自检清单通过（可自检）
  - 准备进入 prd-review

质量门禁:
  - PRD 结构不完整 → 补充完整后再进入评审
```

#### Step 2: PRD 评审 (prd-review)

```yaml
名称: PRD 评审
Agent: 产品经理 Agent / 主 Agent
触发 Skill: prd-review

准入条件:
  - Step 1 完成，PRD 已产出
  - PRD 文档存在于设计目录

执行内容:
  - 按 9 项自检清单逐项评审:
    1. 价值分析
    2. 竞品/调研
    3. 迭代目标
    4. 成功衡量
    5. 产品方案
    6. toC/toB 可落地
    7. 场景描述
    8. 设计产出物
    9. 文档命名规范
  - 产出评审纪要: design/documents/changes/[change-id]/records/PRD-[change-id]-评审纪要.md

产出物:
  - 评审纪要（必须包含 5 章节）:
    1. 评审基本信息
    2. 评审过程记录
    3. 问题发现与处理
    4. 整体评审结论
    5. 附录

准出条件（综合判定）:
  - 通过: 所有自检项均通过（或仅 minor 建议，无阻塞问题）
  - 有条件通过: 存在有条件通过项，但无阻塞性问题（记录优化项）
  - 不通过: 存在不通过项（必须修改 PRD，重新评审）

质量门禁:
  - 不通过 → 退回 Step 1，修改 PRD
  - 有条件通过 → 可并行进入 Step 3，但须在迭代中完成优化

迭代日志记录:
  - "- YYYY-MM-DD | [change-id] | prd-review | PRD 评审完成，综合判定：[通过/有条件通过/不通过]，评审纪要路径：[路径]"
```

#### Step 3: 工程结构分析 (project-analysis)

```yaml
名称: 工程结构分析
Agent: 架构 Agent
触发 Skill: project-analysis

准入条件:
  - Step 2 通过（通过或有条件通过）
  - PRD 评审纪要已产出

执行内容:
  - 分析工程结构与技术实现方案
  - 产出技术方案: openspec/changes/[change-id]/design.md
  - 必须符合 6 章节结构:
    1. 变更目标与范围
    2. 架构与模块
    3. 接口与数据
    4. 关键流程与执行逻辑
    5. 异常、安全与性能
    6. 与需求/PRD 的对应

产出物:
  - 技术方案文档（design.md）
  - 可选: 技术架构图、执行逻辑图、数据流图
  - 可选: project-rules/ 下补充约束文档

准出条件:
  - 技术方案已产出
  - 与 PRD 对应关系明确
  - 准备进入 architecture-review

质量门禁:
  - 技术方案结构不完整 → 补充完整后再进入评审
  - 与 PRD 不一致 → 对齐后再进入评审
```

#### Step 4: 技术方案评审 (architecture-review)

```yaml
名称: 技术方案评审
Agent: 架构 Agent / 主 Agent
触发 Skill: architecture-review

准入条件:
  - Step 3 完成，技术方案已产出
  - 技术方案文档存在于 openspec/changes/[change-id]/

执行内容:
  - 对照 PRD 评审技术方案
  - 按 9 项自检清单逐项评审:
    1. 变更目标与范围
    2. 与 project.md 一致
    3. 与需求/PRD 可追溯
    4. 接口与数据
    5. 关键流程与图示
    6. 异常与边界
    7. project-rules 从属关系
    8. 与 openspec 一致
    9. 文档命名规范
  - 产出评审纪要: design/documents/changes/[change-id]/records/技术方案-[change-id]-评审纪要.md

产出物:
  - 评审纪要（必须包含 5 章节）:
    1. 评审基本信息
    2. 评审过程记录
    3. 问题发现与处理
    4. 整体评审结论
    5. 附录

准出条件（综合判定）:
  - 通过: 所有自检项均通过（或仅 minor 建议，无阻塞问题）
  - 有条件通过: 存在有条件通过项，但无阻塞性问题（记录优化项）
  - 不通过: 存在不通过项（必须修改技术方案，重新评审）

质量门禁:
  - 不通过 → 退回 Step 3，修改技术方案
  - 有条件通过 → 可并行进入 Step 5，但须在迭代中完成优化
  - 技术方案与 PRD 不一致 → 对齐后再进入编码

迭代日志记录:
  - "- YYYY-MM-DD | [change-id] | architecture-review | 技术方案评审完成，综合判定：[通过/有条件通过/不通过]，评审纪要路径：[路径]"
```

#### Step 5: 编码实现 (coding-implement)

```yaml
名称: 编码实现
Agent: 前端 Agent / 后端 Agent
触发 Skill: coding-implement

准入条件:
  - Step 4 通过（通过或有条件通过）
  - 技术方案评审纪要已产出
  - 技术方案与 PRD 对齐

执行内容:
  - 按技术方案实现代码
  - 遵循 project.md 和 project-rules/ 的工程约束
  - 维护相关元信息文档:
    - info-database/（如涉及数据库变更）
    - info-service-interface/（如涉及接口变更）

产出物:
  - 代码文件
  - 可选: 数据库表结构说明与 DDL 脚本
  - 可选: 接口说明文档

准出条件:
  - 代码实现完成
  - 自检通过（实现完成自检）
  - 准备进入 code-review

质量门禁:
  - 实现与技术方案不符 → 调整实现或更新技术方案
  - 自检不通过 → 修复问题后再进入评审
```

#### Step 6: 代码评审 (code-review)

```yaml
名称: 代码评审
Agent: 架构 Agent
触发 Skill: code-review

准入条件:
  - Step 5 完成，代码已实现
  - 实现自检通过

执行内容:
  - 对照技术方案评审代码
  - 检查维度:
    - 需求符合性（是否实现 PRD 所有功能点）
    - 架构分层（是否符合架构设计）
    - 代码质量（可读性、可维护性）
    - 安全/性能（是否满足非功能性要求）
    - 日志与监控（是否可观测）
    - 测试覆盖（是否充分测试）
  - 产出评审记录: design/documents/changes/[change-id]/records/[change-id]-code-review.md

产出物:
  - 代码评审记录（包含问题清单与后续行动）

准出条件:
  - 无 Blocking/Major 级问题
  - 或问题已转化为 tasks.md 中的任务并计划修复

质量门禁:
  - 存在 Blocking 问题 → 修复后才能进入验收
  - Major 问题 → 评估后决定是否修复或记录为技术债务

协同关系:
  - 与 coding-implement 形成「实现 → 评审 → 迭代」闭环
  - 发现问题可回溯到需求/架构层，建议更新相关文档
```

#### Step 7: 功能验收 (func-test)

```yaml
名称: 功能验收
Agent: 测试 Agent
触发 Skill: func-test

准入条件:
  - Step 6 完成，代码评审通过
  - 代码已合并或准备合并

执行内容:
  - 对照 specs 中 Requirements + Scenarios 执行测试
  - 对照需求验收 Checklist 逐项验证
  - 执行两轮 OpenSpec validate:
    - 第一轮: openspec validate [change-id]（验证一致性）
    - 第二轮: openspec validate --strict（严格模式，验收通过后执行）
  - 产出验收记录: design/documents/changes/[change-id]/records/[change-id]-func-test.md

产出物:
  - 验收记录（包含测试用例、测试结果、validate 结果）

准出条件:
  - 所有验收 Checklist 项通过
  - 或问题已修复并重新验证
  - openspec validate --strict 通过

质量门禁:
  - 关键功能未通过 → 修复后重新验收
  - validate 不通过 → 对齐文档与实现

协同关系:
  - 与 coding-implement、code-review 形成「实现 → 评审 → 验收」质量闭环
  - 测试中发现的需求/架构问题，反向推动文档与规范修订
```

#### Step 8: 归档完成

```yaml
名称: 归档完成
Agent: 主 Agent / 自动流程
触发: 验收通过后自动触发

执行内容:
  - 更新 tasks.md，勾选所有已完成任务
  - 执行 openspec archive [change-id]（归档到 specs/）
  - 更新迭代日志，标记变更完成
  - 触发 Step 9（复盘）判断

产出物:
  - 归档的 spec（openspec/specs/[capability]/spec.md）
  - 完整的 records/ 目录（评审纪要、验收记录等）
  - 触发复盘判断标记

准出条件:
  - 所有任务已完成
  - 验收通过
  - 文档完整归档
  - 已评估是否需要复盘

衔接下一步:
  条件: 归档完成
  下一步: Step 9 (retrospective-analysis) - 如满足复盘触发条件
  触发方式: 自动建议或用户指令
```

#### Step 9: 复盘与持续改进

```yaml
名称: 复盘与持续改进
Agent: 主 Agent / 架构 Agent / 产品经理 Agent（根据复盘类型）
Skill: retrospective-analysis
触发: 以下任一条件满足即触发

触发条件（满足任一）:
  条件 1: 完成重要里程碑后
    - 定义: change-id 完成归档
    - 动作: 主 Agent 自动建议「是否复盘？」
    
  条件 2: 问题反复出现时
    - 定义: 同类问题在 ≥2 个 change-id 中出现
    - 动作: Agent 提示「建议复盘分析根因」
    
  条件 3: 用户明确指令
    - 指令: 「复盘」「总结」「回顾」「反思」
    - 动作: 立即执行 retrospective-analysis
    
  条件 4: 定期复盘
    - 周期: 每周/每月/每季度
    - 动作: Agent 主动发起

执行内容:
  - 执行 5 阶段复盘法
  - 产出复盘报告
  - 沉淀 memory（如评估有价值）
  - 更新迭代日志

产出物:
  - 复盘报告: design/documents/changes/[change-id]/records/复盘报告-YYYYMMDD-主题.md
  - Memory 沉淀: memory/{patterns,anti-patterns,preferences,playbooks,reflections}/
  - 迭代日志更新
  - 改进行动计划

准出条件:
  - 复盘报告完成（通过 9 项自检）
  - 关键经验已评估是否沉淀
  - 改进行动已明确
  - 迭代日志已更新

质量门禁:
  - 通过 9 项自检（≥7 项通过）
  - 有明确行动计划
  - 不能流于形式
```

## 关键质量门禁

| 步骤 | 准入条件 | 准出条件 | 质量门禁（不通过时） |
|-----|---------|---------|-------------------|
| Step 1 | 需求提出 | PRD 产出 | 结构不完整 → 补充 |
| Step 2 | PRD 产出 | 评审通过 | 不通过 → 退回 Step 1；有条件通过 → 记录优化项 |
| Step 3 | PRD 评审通过 | 技术方案产出 | 与 PRD 不一致 → 对齐 |
| Step 4 | 技术方案产出 | 评审通过 | 不通过 → 退回 Step 3；有条件通过 → 记录优化项 |
| Step 5 | 技术方案评审通过 | 代码实现 | 与方案不符 → 调整 |
| Step 6 | 代码实现 | 评审通过 | Blocking 问题 → 修复 |
| Step 7 | 代码评审通过 | 验收通过 | 不通过 → 修复后重验 |
| Step 8 | 验收通过 | 归档完成 | - |
| Step 9 | 满足复盘触发条件 | 复盘完成 | 质量不通过 → 补充分析 |

## 复盘触发条件（确定性执行目标）

复盘不是「可选」步骤，而是满足以下条件**必须触发**：

```yaml
触发条件（满足任一即触发）:
  条件 1: 完成重要里程碑后
    判定标准: change-id 完成归档（Step 8 结束）
    触发动作: 主 Agent 自动建议「是否进行复盘？」
    用户响应: 用户可确认「复盘」或「跳过」（需说明理由）
    
  条件 2: 问题反复出现时
    判定标准: 同类问题在 ≥2 个不同 change-id 中出现
    触发动作: Agent 主动提示「检测到同类问题重复出现，建议进行复盘分析根因」
    必须执行: 问题型复盘必须执行，不可跳过
    
  条件 3: 用户明确指令
    判定标准: 用户输入「复盘」「总结」「回顾」「反思」等关键词
    触发动作: 立即执行 retrospective-analysis skill
    必须执行: 用户指令型复盘必须执行
    
  条件 4: 定期复盘
    判定标准: 每周/每月/每季度周期到达
    触发动作: Agent 主动发起「定期复盘时间到了，是否进行复盘？」
    用户响应: 用户可确认「复盘」或「延期」（需设置新时间）

跳过复盘的记录:
  如果用户选择跳过复盘，必须在迭代日志中记录:
  "- YYYY-MM-DD | [change-id] | retrospective-analysis | 用户选择跳过复盘，理由：[理由]"
  
  问题型复盘不允许跳过，必须执行。
```

## 适用场景

### 必须使用

| 场景 | 说明 |
|-----|------|
| **新项目启动** | 首个 change-id 必须按完整闭环执行 |
| **重大功能迭代** | 涉及架构调整、新增能力、重大变更 |
| **跨团队协作** | 需要异步协作、文档驱动、质量可追溯 |
| **质量敏感项目** | 对质量要求高，需要详细审计记录 |

### 推荐使用

| 场景 | 说明 |
|-----|------|
| **小型功能迭代** | 可简化部分步骤，但核心评审不可少 |
| **技术债务偿还** | 需要评估、方案、实现、验收完整闭环 |
| **重构改造** | 必须评审技术方案，确保架构合理性 |
| **新人培训** | 通过完整闭环让新人理解规范 |

### 可简化使用

| 场景 | 简化方式 |
|-----|---------|
| **文档微调** | 跳过编码、代码评审、功能验收 |
| **Hotfix** | 紧急修复，可简化 PRD/技术方案评审，但需事后补录 |
| **实验性探索** | 可简化部分评审，但需明确实验范围 |

## 收益

| 维度 | 改进前 | 改进后 |
|-----|-------|--------|
| **质量可追溯** | 无法追溯设计决策 | 评审纪要详细记录决策逻辑 |
| **质量可审计** | 审计时无据可查 | 评审纪要作为审计依据 |
| **质量一致性** | 依赖个人经验，波动大 | 标准化评审清单，质量可控 |
| **知识传承** | 经验随人走 | 评审纪要沉淀为记忆 |
| **协作效率** | 会议驱动，成本高 | 文档驱动，异步协作 |
| **问题定位** | 难以定位问题根因 | 分阶段评审，精准定位 |
