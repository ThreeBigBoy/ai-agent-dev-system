# 强制记录日志机制 — 详尽模拟

本文档对「在 change-id 下完成调用后必须追加迭代日志」的**强制记录日志机制**做一次完整、逐步骤的模拟，用于验证触发条件、执行路径、角色依赖与残留缺口。规范来源：`projects-rules-for-agent.md`、`skills-rules-for-agent.md`、`主Agent.md`、`.cursor/rules/global-rules.mdc`。

---

## 一、机制全貌（规范摘要）

### 1.1 触发条件（何时必须写日志）

| 条件 | 说明 |
|------|------|
| **有 change-id 上下文** | 本次调用在某一变更（change-id）下进行，即任务明确关联到 `design/documents/[change-id]/` 或 `openspec/changes/[change-id]/`。 |
| **本次调用有产出** | 完成本次 Agent/技能调用并产生了可交付的产出（代码、文档、验收记录等）。 |
| **本轮对话内** | 须在同一轮对话内完成追加，不得留待他人或后续会话补录。 |

**豁免**：无明确 change-id（如泛化咨询、非变更类任务）时可跳过。

### 1.2 规范来源与条款位置

| 规范文件 | 条款位置 | 要点 |
|----------|----------|------|
| **projects-rules-for-agent.md** | 「执行后必做收尾动作」表 + 「收尾自检（完成性回复前必做）」+ 「Agent 与技能调用迭代日志」整节 | 收尾定义、路径、格式、自检与禁止表述 |
| **skills-rules-for-agent.md** | 开篇「执行后必做收尾（通用，所有技能均适用）」；9.1 request-analysis 第 6 条 | 任意技能执行后须追加；9.1 再次强调 |
| **主Agent.md** | 「执行规范（要点）」→ 收尾（必做） | 主 Agent 及所协调子 Agent 须在同一轮内追加；完成性/交付性回复前自检 |
| **global-rules.mdc** | 对话开始时须读 projects-rules、skills-rules | 首条消息时加载两规则，从而带入收尾与自检约定 |

### 1.3 执行方与路径

- **谁写**：本次执行方（主 Agent 或当前承担任务的子 Agent），不得留待他人补录。
- **路径**：`design/documents/[change-id]/records/迭代日志.md` 或 `[change-id]-iteration-log.md`；文件不存在则新建。
- **单条格式**：`XXXX年XX月XX日 HH:mm:ss：XX Agent，调用了 XX 技能，处理 XX 任务，输出 XX；使用模型 XX。`（格式详见 projects-rules「Agent 与技能调用迭代日志」。）

### 1.4 收尾自检与禁止表述

- **自检时机**：在向用户作出**任何表示向用户交付本轮产出的总结性回复**（如「任务已完成」「已闭环」「已交付」「改好了」「已落实」「请验收」等）**之前**。
- **自检内容**：是否已向上述迭代日志文档**追加本条**。
- **若未追加**：须**先完成追加，再**作出该回复。
- **禁止**：在未完成迭代日志追加的情况下使用上述完成性/交付性表述。

## 二、入口与 change-id 上下文的形成

### 2.1 用户话术与任务类型（是否必然带出 change-id）

| 用户话术类型 | 是否通常带出 change-id | 说明 |
|--------------|------------------------|------|
| 「推进 update-theme-v1.0.1 的 2.2」「完成 tasks 里 1.4」 | ✅ 是 | 明确指向某变更/某任务，change-id 可从 proposal、tasks 路径得出。 |
| 「按这个需求出方案」「做 XXX 功能的迭代」 | ✅ 是（新建变更） | 按 OpenSpec 第六节会先建 design/documents/[change-id]/，再建 openspec/changes/[change-id]/，change-id 在首步即确定。 |
| 「修一下 footer 的 bug」「把首页 banner 改个文案」 | ⚠️ 可能无 | 若用户未提 change-id、当前对话也未关联某变更目录，则可能被判定为「无明确 change-id」而跳过收尾。 |
| 「解释一下 OpenSpec 第六节」「Liquid 里 section 怎么用」 | ❌ 否 | 泛化咨询、非变更类，可跳过。 |

结论：**只有任务明确关联到某一变更目录或 tasks/proposal 时，强制日志机制才生效**；模糊请求需主 Agent 或执行方先明确「是否挂到某 change-id」，否则合规跳过。

### 2.2 进入 change-id 上下文的典型路径

1. **新建变更**：用户发起新需求/迭代 → 按 OpenSpec 第六节创建 `design/documents/[change-id]/` 与 `openspec/changes/[change-id]/` → 后续所有在该变更下的产出均属该 change-id 上下文。
2. **推进既有任务**：用户说「推进 2.2」→ 主 Agent 读 `openspec/changes/[change-id]/tasks.md` 等 → 执行方在该 change-id 下实现/验收 → 产出归属该 change-id。
3. **主 Agent 指派时明确**：主 Agent 在拆解或指派时说明「本次在 change-id=xxx 下执行」，则执行方在该上下文中产出后须写日志。

## 三、角色与阅读依赖（谁在什么情况下「知道」要写日志）

### 3.1 主 Agent

| 阅读来源 | 是否包含收尾/自检约定 | 何时加载 |
|----------|------------------------|----------|
| global-rules.mdc | 无直接收尾条文；要求先读 projects-rules、skills-rules | 对话开始时（若遵守「第一条消息时」动作） |
| projects-rules-for-agent.md | ✅ 有：执行后必做收尾、收尾自检、禁止表述、迭代日志格式 | 同上 |
| skills-rules-for-agent.md | ✅ 有：执行后必做收尾（通用） | 同上 |
| 主Agent.md | ✅ 有：收尾（必做）+ 完成性回复前自检 + 禁止表述 | 若配置为主 Agent 身份则加载 |

结论：主 Agent 若在对话开始时按 global-rules.mdc 读取 projects-rules 与 skills-rules，且身份配置加载主Agent.md，则**具备完整的收尾与自检约定**；在作出完成性/交付性回复前会看到「须自检→未追加则先追加再回复」。

### 3.2 子 Agent（如前端 Agent、测试 Agent）

| 阅读来源 | 是否包含收尾/自检约定 | 说明 |
|----------|------------------------|------|
| global-rules.mdc | 无直接收尾；要求读 projects-rules、skills-rules | 子 Agent 若在同一 Cursor 规则下，理论上也会被要求先读这两份；若子 Agent 以「另一会话/仅读 SKILL」方式运行，可能只读 SKILL。 |
| projects-rules-for-agent.md | ✅ 有 | 仅当该会话/该身份实际加载了 projects-rules 时可见。 |
| skills-rules-for-agent.md | ✅ 有（开篇通用段 + 9.1） | 若只扫 9.3/9.4/9.5 而未读开篇，可能漏掉开篇的「执行后必做收尾（通用）」；读开篇则可见。 |
| 本角色 SKILL.md（如 coding-implement/SKILL.md） | ❓ 当前未强制要求 | 多数 SKILL 未在步骤末尾显式写「向 records/迭代日志.md 追加一条」，故**仅读 SKILL 不读 rules 的子 Agent 可能不知道要写日志**。 |

结论：子 Agent 的收尾执行依赖**是否在会话中加载了 projects-rules 或 skills-rules 开篇**。若主 Agent 在指派时未强调「完成后须写迭代日志」且子 Agent 仅读 SKILL，存在**漏执行风险**；当前已在 skills-rules 开篇加通用收尾段，可减轻但未完全消除该风险。

### 3.3 阅读顺序与遗漏风险（简要）

- **理想链**：global-rules.mdc（首条消息）→ 读 projects-rules + skills-rules → 执行方确定 → 读 SKILL → 执行 → 产出 → **回复前自检** → 未追加则先追加 → 再回复。
- **断链点**：① 首条未读 rules（如用户直接问「改个文案」未触发规范入口）；② 执行方仅读 SKILL、未读 rules；③ 回复时未进行「完成性/交付性」自检，或用了未在列举中的表述（如「搞定了」）且未识别为交付性回复。

## 四、时间线模拟（单次任务从发起到闭环）

以下为**理想遵守规范**下的单次任务时间线；每步后括号内标出对应的规范依据。

1. **用户发起**  
   用户：「推进 update-theme-v1.0.1-mvp-editor-ux 的 2.2。」  
   → change-id = `update-theme-v1.0.1-mvp-editor-ux`，上下文明确。

2. **主 Agent 或执行方加载规范**  
   若遵守 global-rules.mdc：读取 projects-rules、skills-rules；执行方（如前端 Agent）按 skills-rules 读 coding-implement SKILL.md。  
   → 执行方若读过 projects-rules 或 skills-rules 开篇，则知「执行后必做收尾」与「完成性回复前自检」。

3. **执行前自检**  
   projects-rules 执行前自检清单含「迭代日志：是否已约定并在本次调用产出完成后向 records/迭代日志.md 追加一条」。  
   → 自检通过后开始实施。

4. **执行与产出**  
   前端 Agent 按 SKILL 完成代码修改、更新 tasks 等；产出落盘。

5. **回复前收尾自检（关键）**  
   执行方在组织回复时：若打算说「2.2 已实现」「改好了请验收」等，则触发「完成性/交付性回复前必做」自检：是否已向 `design/documents/update-theme-v1.0.1-mvp-editor-ux/records/迭代日志.md` 追加本条？  
   → 若未追加：**先**写日志（含时间、Agent、技能、任务、输出、使用模型），**再**回复用户。  
   → 若已追加：可直接回复。

6. **回复用户**  
   在 5 完成后，执行方作出总结性/交付性回复；规范禁止在未追加时使用完成性/交付性表述，故合规路径下不会出现「先说完成却未写日志」的回复。

7. **主 Agent 事后核对（可选）**  
   projects-rules「执行到位」：主 Agent 在统筹、验收或归档前可核对该变更的 `records/迭代日志.md` 是否与本次迭代内的 Agent/技能调用一致；若发现缺失，须补录或要求执行方补录后再闭环。

## 五、场景枚举与预期行为

| 场景 | change-id | 预期行为 | 可能缺口 |
|------|-----------|----------|----------|
| 主 Agent 审核提案并回复「已审核，通过」 | 有 | 回复前自检→未追加则先追加再回复 | 若主 Agent 未读 projects-rules/主Agent，可能忘记自检。 |
| 前端 Agent 完成 2.2 实现，回复「2.2 已实现，请验收」 | 有 | 同上 | 若该会话只读了 SKILL 未读 rules，可能不写日志。 |
| 用户「修一下 footer 的 bug」，未提 change-id | 可能无 | 若未关联到某变更目录，可跳过收尾 | 若实际应挂到某 change-id，需主 Agent 或执行方先明确。 |
| 多轮对话中仅做中间汇报（如「目前已完成 1/3」） | 有 | 若该轮有可交付产出且后续会作完成性回复，应在**该轮**或**最终完成性回复前**追加 | 若把「中间汇报」也视为交付性回复，则当轮就应追加；规范未明确「中间汇报」是否算交付性回复，建议视为：有产出且本轮回复为总结/交付则当轮追加。 |
| 主 Agent 代子 Agent 向用户汇报「前端已完成 2.2」 | 有 | 主 Agent 代汇报时，应由**执行方（前端）**在该轮对话内已追加；若主 Agent 代汇报且执行方未追加，主 Agent 应补录或要求执行方补录后再代汇报。 | 跨会话时代汇报：若执行方未写日志，主 Agent 需能发现并补录（如核对 records/迭代日志.md）。 |
| 测试 Agent 产出验收记录，回复「验收记录已写入，X 通过 Y 不通过」 | 有 | 回复前自检→未追加则先追加再回复 | 同子 Agent：依赖是否加载 rules。 |
| 产品经理产出 proposal + tasks，回复「提案和 tasks 已写好」 | 有 | 同上 | 9.1 明确有迭代日志收尾，产品经理若读 skills-rules 9.1 会看到。 |

## 六、边界与例外（规范原文要点）

- **无明确 change-id**：泛化咨询、非变更类任务时可跳过收尾。（projects-rules、skills-rules 通用段。）
- **同一轮对话内**：须由本次执行方在同一轮对话内完成追加，不得留待他人或后续会话补录。（projects-rules 收尾表。）
- **文件不存在**：则新建迭代日志文件后再追加。（projects-rules「Agent 与技能调用迭代日志」。）
- **时间与格式**：时间以沙箱本地时间为准，单条含 Agent、技能、任务、输出、**使用模型**。（同上。）

## 七、残留缺口与加固建议

### 7.1 残留缺口（无法从机制上 100% 保证的原因）

| 缺口 | 说明 |
|------|------|
| **依赖「读规范」** | 机制建立在 Agent 已读 projects-rules / skills-rules / 主Agent 的前提下；若某会话未加载这些规则（如仅打开 SKILL），收尾约定不可见。 |
| **无程序化校验** | 没有脚本或工具在「回复发送前」检查是否已追加日志，无法从系统层面强制 100%。 |
| **完成性/交付性表述的边界** | 规范已列举「改好了」「已落实」「请验收」等，但若出现新的说法（如「可以看了」）且 Agent 未识别为交付性回复，仍可能先回复后忘记写日志。 |
| **子 Agent 独立会话** | 若子 Agent 在另一会话中执行且该会话未配置加载 global-rules 或 projects-rules，不会看到收尾要求。 |

### 7.2 已做的加固（当前规范状态）

- 执行后必做收尾 + 收尾自检（完成性回复前必做）+ 禁止未追加时使用完成性/交付性表述（projects-rules、主Agent）。
- 扩大「完成性表述」为包含「任何表示向用户交付本轮产出的总结性回复」（如「改好了」「已落实」「请验收」等）（projects-rules、主Agent）。
- skills-rules 开篇增加「执行后必做收尾（通用，所有技能均适用）」，使任意技能执行方只要读 skills-rules 开篇即能看到收尾要求。
- 主 Agent 在统筹/验收/归档前可核对 `records/迭代日志.md` 并补录或要求执行方补录（projects-rules「执行到位」）。

### 7.3 可选进一步加固

- **各技能 SKILL.md 末尾**：在「产出/收尾」步骤中显式增加一条：「向 `design/documents/[change-id]/records/迭代日志.md` 追加一条记录，格式见 projects-rules-for-agent.md『Agent 与技能调用迭代日志』。」这样仅读 SKILL 的执行方也会看到。
- **OpenSpec/AGENTS.md 或变更检查清单**：增加验收项「本变更下本次会话/本任务是否已向 records/迭代日志.md 追加本条」，由主 Agent 或人工在闭环前勾选。
- **主 Agent 代汇报时**：在 主Agent.md 或 projects-rules 中明确「代子 Agent 向用户作完成性汇报前，须确认该执行方已在本轮或本会话内追加迭代日志；若未追加，由主 Agent 补录或要求执行方补录后再代汇报」。

## 八、机制生效情况检查（本对话及此前模拟）

以下对照「执行后必做收尾 + 收尾自检」逐步检查：**此前几次模拟对话**与**本对话**是否满足触发条件、为何未在当轮记录日志、以及本次补录说明。

### 8.1 检查步骤（逐条对照）

| 步骤 | 检查项 | 此前模拟 / 本对话情况 | 结论 |
|------|--------|------------------------|------|
| 1 | **是否有 change-id 上下文？** | 此前模拟：讨论与修订的是 ai-agent-dev-system 下的 global-rules、主Agent、skills-rules 及本模拟文档，未明确挂到某一项目变更（如 update-theme-v1.0.1-mvp-editor-ux）下执行任务。本对话：用户要求「对照执行依次机制生效情况检查」，并指出「这几次模拟仍然没有记录日志」，本对话产出为机制生效检查与补录。 | 此前模拟可视为**无明确 change-id**（规范修订与模拟属 ai-agent-dev-system，非某单一 OpenSpec 变更）；本对话若将「机制检查与补录」视为对使用该机制的项目（如 Proj01ShopifyTheme 的 update-theme-v1.0.1-mvp-editor-ux）的配套动作，则**可关联**该 change-id 并补录。 |
| 2 | **本次调用是否有产出？** | 是。此前：projects-rules、skills-rules、主Agent 的收尾/自检条款修订，以及本模拟文档的撰写。本对话：本段「机制生效情况检查」增补 + 向该变更迭代日志补录本条。 | ✅ 有产出 |
| 3 | **是否在作出完成性/交付性回复前执行了收尾自检？** | 此前模拟：在给出「模拟结论」「已做强化」等总结性回复时，**未**先自检「是否已追加迭代日志」，也**未**先追加再回复，直接作出了交付性表述。本对话：在用户指出未记录日志后，执行本检查并补录。 | ❌ 此前未执行自检 → **机制未生效**；本对话在补录后作出本回复，符合「先追加再回复」。 |
| 4 | **是否在同一轮对话内追加了记录？** | 此前：未追加。本对话：在本轮内向 `design/documents/update-theme-v1.0.1-mvp-editor-ux/records/迭代日志.md` 追加一条（机制生效情况检查后补录）。 | 本对话 ✅ 已补录 |

### 8.2 原因分析（为何此前模拟未记录日志）

1. **未将「模拟/规范修订」关联到具体 change-id**：模拟时以「主 Agent 在 change-id 下完成任务」为假设场景，但执行模拟的会话本身在修改 ai-agent-dev-system，未显式认定「本会话产出归属某项目的某 change-id」，故未触发向该 change 的 records 追加。
2. **完成性回复前未执行收尾自检**：即便规范已写「作出完成性/交付性回复前须自检」，在实际回复「模拟结论」「已做强化」时，未在输出前执行「是否已追加本条？未追加则先追加再回复」的步骤，说明**自检依赖 Agent 主动执行**，易被遗漏。
3. **对话目标被理解为「只做规则设计」**：Agent 将任务理解为修订规范与写模拟文档，未同时把「在本轮内对某一 change 追加日志」视为必做收尾，暴露出**跨仓库/跨 change 的会话**下 change-id 归属不清晰时，收尾易被跳过。
