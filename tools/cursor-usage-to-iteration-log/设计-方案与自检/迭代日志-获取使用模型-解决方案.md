# 在 Cursor 桌面端获取「具体使用模型」用于迭代日志 — 解决方案

**诉求**：通过插件/监听方式，在每次 Agent 执行并记录迭代日志时，自动获取具体使用模型信息（含 Auto 模式）。要求长期可用、自动化。

**结论（简要）**：  
当前 **Cursor 不向扩展或本地 API 暴露「本次 Composer/Agent 实际使用的模型」**（含 Auto 模式下被路由到的具体模型）。因此**不存在**「完全自动、从 Cursor 内部拿到每次执行模型」的现成插件或官方能力。下面给出**可长期使用的替代方案**与**若 Cursor 未来开放能力时的推荐做法**。

**落地方案（已实现）**：通过 **Cursor Usage Monitor 同源 API** + **Python 脚本** 在每次 Agent 写迭代日志前拉取「最近一次请求的模型」并写入日志，见 **`ai-agent-dev-system/tools/cursor-usage-to-iteration-log/README.md`** 与 **`projects-rules-for-agent.md`** 中「使用模型」优先级 ①。

---

## 一、现状与限制

| 能力/来源 | 是否可用 | 说明 |
|----------|----------|------|
| **Cursor 扩展 API** | ❌ 不暴露 | Cursor 基于 VS Code，扩展使用标准 VS Code API；**无** Cursor 专属 API 提供「当前/本次请求的模型名」。 |
| **Auto 模式实际模型** | ❌ 不暴露 | 官方与社区均确认：Auto 不会在回复或上下文中告知本次实际使用的模型。 |
| **Analytics API（团队）** | ⚠️ 仅聚合 | Enterprise 可用，提供按**日**、按模型的消息数等；**无**单次请求或单次会话的模型字段，无法与「本次 Agent 执行」一一对应。 |
| **本地日志** | ❓ 未验证 | Cursor 在 `~/Library/Application Support/Cursor/logs/`（macOS）等路径有日志；是否包含「每次请求的模型名」需自行抓包/查看，且格式可能随版本变化，**不适合作为长期稳定数据源**。 |

因此：**仅靠「插件监听 Cursor 内部」在目前无法可靠、长期地拿到每次执行的具体模型（含 Auto）。**

---

## 二、可行方案（按推荐度）

### 方案 A：工作区「当前模型」文件 + Agent 读文件（推荐，长期可用）

**思路**：在项目内约定一个**仅由用户或本地工具写入**的「当前用于迭代日志的模型」文件；Agent 在**每次追加迭代日志前**读取该文件，若存在则用其值作为「使用模型」，否则用「Auto（具体模型未暴露）」或「—」。

**步骤**：

1. **约定路径**（二选一或项目自定）  
   - 项目根下：`.cursor/current-model-for-iteration-log.txt`  
   - 或按变更：`design/documents/[change-id]/records/.current-model.txt`

2. **文件内容**  
   单行纯文本，即本次希望记入迭代日志的模型名，例如：  
   `Claude 4.6 Sonnet`、`Auto（具体模型未暴露）`、`Composer 1.5`、`GPT-5.2` 等。

3. **谁写入**  
   - **方式 1（手动）**：切换模型或开始一次 Agent 会话前，用户（或脚本）写入/覆盖该文件。  
   - **方式 2（半自动）**：用下方「方案 B」的 VS Code 扩展命令或快捷键写入。

4. **Agent 行为**（写入规范）  
   在 `projects-rules-for-agent.md` 的迭代日志格式中约定：  
   - 追加迭代日志时，**先读取**上述约定路径；  
   - 若文件存在且非空，则「使用模型」取该文件内容（trim 后）；  
   - 若不存在或为空，则按现有规则：用户在本轮说明则用说明，否则 Auto 填「Auto（具体模型未暴露）」，完全未知填「—」。

5. **可选**：写日志成功后清空该文件，避免下次误用旧值；或保留直到用户下次修改（视习惯而定）。

**优点**：不依赖 Cursor 内部 API；跨平台、长期有效；与现有「使用模型」规范兼容。  
**缺点**：需用户（或扩展）在切换/使用前维护该文件，非「全自动从 Cursor 读出」。

---

### 方案 B：VS Code 扩展「设置当前迭代日志用模型」

**思路**：做一个**小型 VS Code/Cursor 扩展**，提供命令（如 `Cursor: Set model for iteration log`）或状态栏入口，将用户选择的模型名写入方案 A 的约定文件；Agent 仍按方案 A 读该文件。

**实现要点**：

- 使用 **VS Code Extension API**（`workspace.fs` 或 `vscode.workspace.getConfiguration` + 工作区 `.vscode` 下某配置亦可，但统一用文件更简单）。
- 命令：弹出 QuickPick 或 InputBox，选项包含「Claude 4.6 Sonnet」「Composer 1.5」「Auto（具体模型未暴露）」等；选定后写入 `.cursor/current-model-for-iteration-log.txt`（或项目约定路径）。
- 可绑定快捷键，便于「每次跑完 Agent 点一下」或「切换模型后点一下」。
- **不依赖** Cursor 暴露当前模型；只是把「用户已知的模型」持久化到约定文件，供 Agent 读取。

**发布**：可仅本地安装（vsce package → 从 VSIX 安装），或按 Cursor 文档发布到 Open VSX 供团队使用。

**优点**：一次配置、长期可用；与方案 A 组合即「半自动」：用户选一次，Agent 写日志时自动带出模型。  
**缺点**：仍非从 Cursor 内部自动获取；Auto 时若用户选「Auto（具体模型未暴露）」则与现在行为一致，无法得到 Auto 实际路由到的模型。

---

### 方案 C：Analytics API（仅 Enterprise）— 仅作参考，无法对应单次执行

若团队为 **Cursor Enterprise** 且仅需**统计/复盘**某段时间用了哪些模型，可用 [Analytics API](https://cursor.com/docs/account/teams/analytics-api)：

- `GET /analytics/team/models`：按日、按模型的 `messages` / `users` 聚合。  
- `GET /analytics/by-user/models`：按用户、按日、按模型的用量。

**限制**：数据为**按日聚合**，无「单次 Composer 请求 ↔ 模型」对应关系，**不能**在「Agent 执行并写日志」的瞬间拿到「本次使用的模型」。  
**适用**：看团队/个人一段时间内模型分布，而非每条迭代日志的「使用模型」字段。

---

### 方案 D：向 Cursor 提功能请求（长期）

建议向 Cursor 官方（论坛 / 反馈）提出：

- **桌面端**：在 Composer/Agent 完成一次请求后，将「本次实际使用的模型」（含 Auto 路由结果）写入工作区可读位置之一：  
  - 工作区状态（如 `vscode.workspace.getConfiguration` 下某 key），或  
  - 约定路径下的文件（如 `.cursor/last-composer-model.txt`），或  
  - 通过 MCP / 扩展 API 提供「last used model」查询。

若将来实现，则可做「真·全自动」：扩展或 Agent 在写迭代日志前读该状态/文件即可。

---

### 方案 E：Cursor 提供 `events.subscribe('ai.request')` 且 payload 含实际 model（若存在则可彻底解决）

若 Cursor 提供 **`@cursor-sdk/core`**（或同类 SDK/扩展 API），并支持 **`events.subscribe('ai.request', (event) => { ... })`**，且 **`event.payload.model`** 为本次请求**实际使用的模型**（含 Auto 模式下的路由结果），则可用如下方式**彻底解决**获取真实模型的问题：

- 在扩展或本地脚本中监听 `ai.request`，将 `event.payload.model`（及可选 requestId、timestamp）写入约定文件（如 `.cursor/current-model-for-iteration-log.txt` 或 `~/.cursor/ai-logs.jsonl`）。
- Agent 在追加迭代日志前读取该文件（或最近一行）即可得到真实模型名。

**截至当前查证**：npm 上 **不存在** 公开的 `@cursor-sdk/core` 包（404），Cursor 官方文档也未列出该 SDK 或 `ai.request` 事件。若你从内部文档、Beta 或社区获得该示例，建议先确认其是否在你这边的 Cursor 版本/渠道可用；若尚未开放，可向 Cursor 提功能请求，请求提供「AI 请求事件 + payload 中含实际使用模型」的扩展/SDK 能力。

## 三、插件推荐与自建建议

| 类型 | 说明 |
|------|------|
| **现成插件** | **目前没有**能在 Cursor 桌面端「监听 Agent 执行并拿到具体使用模型（含 Auto）」的公开插件；因 Cursor 未暴露该数据。 |
| **推荐做法** | **自建小型 VS Code 扩展**（方案 B），实现「设置当前迭代日志用模型」并写入约定文件，与方案 A 配合，形成**长期可用的半自动方案**。 |
| **可选** | 用 **MCP 服务**提供「设置/读取当前模型」接口，Agent 写日志时通过 MCP 取当前模型；数据源仍可为上述约定文件，由本地脚本或扩展写入。 |

## 四、规范与工程落地建议

1. **在 `projects-rules-for-agent.md` 中约定**  
   - 迭代日志「使用模型」的取值优先级：  
     1）若项目内约定路径存在「当前模型」文件且非空，则用其内容；  
     2）否则按现有规则（用户说明 > Auto（具体模型未暴露）> 「—」）。  
   - 约定路径示例：`.cursor/current-model-for-iteration-log.txt`（或 `design/documents/[change-id]/records/.current-model.txt`）。

2. **在 `design/documents/[change-id]/records/README.md` 或项目 README**  
   - 简短说明：若需在迭代日志中记录具体模型，请在使用 Agent 前设置「当前模型」文件（或使用 XX 扩展命令）。

3. **扩展实现**  
   - 仓库中可增加 `tools/cursor-iteration-log-model/`（或类似）目录，放置扩展源码与 README，说明安装方式与命令/快捷键。

这样即可在**不依赖 Cursor 暴露内部模型**的前提下，得到**长期可用、可自动化的「使用模型」记录方案**；若 Cursor 未来开放「本次请求模型」，再接入即可升级为全自动。

## 五、关于 Cursor Usage / AG Usage / Cursor Usage Monitor 等插件

以下为常见「用量类」插件的用途与是否可用于**监听 Auto 模式下具体使用模型**的结论。

| 插件 | 类型 | 是否能看到「每条请求的模型」 | 是否含 Auto 实际模型 | 能否自动写入迭代日志 |
|------|------|------------------------------|----------------------|----------------------|
| **Cursor Usage Monitor** | VS Code/Cursor 扩展（lixen.cursor-usage） | ✅ 是 | ⚠️ 可能 | ❌ 不能 |
| **Cursor Usage** | Chrome 浏览器扩展 | ✅ 按模型统计 | ⚠️ 可能 | ❌ 不能 |
| **AG Usage** | 多为「Auto + API 用量」类扩展的简称或变体 | 视具体插件而定，通常同左 | ⚠️ 可能 | ❌ 不能 |

**说明**：

- **Cursor Usage Monitor**（VS Code 扩展）：从 Cursor 的**用户用量 API**（与 dashboard 同源）拉取数据，功能包括 **「Activity History: View recent requests with model, tokens, and cost」**。即：**最近请求列表里带「model」字段**，可用于**人工查看**每次请求（含 Composer/Agent）使用的模型。若 Cursor 后端在 Auto 请求时也记录并返回实际路由到的模型名，则你在 Activity 列表里就能看到 **Auto 下的实际使用模型**。该扩展**不提供**「把当前/最近一次模型写入工作区文件」的功能，因此**不能**直接用于迭代日志的自动填写；可作**辅助**：跑完 Agent 后打开详情面板，看最近一条的 model，再手动写入 `.cursor/current-model-for-iteration-log.txt` 或下次写日志前口述给 Agent。
- **Cursor Usage**（Chrome 扩展）：在浏览器里查看 Cursor 用量，有按模型、按时间等统计，数据来源与网页端 dashboard 一致。适合在**浏览器端**看用量与模型分布，**不能**在 Cursor 桌面端「监听」或写入迭代日志；若 dashboard 的「最近请求」里含每条模型且包含 Auto 实际模型，则同样只能**人工查看**后自行填入约定文件或告知 Agent。
- **AG Usage**：名称常指「Auto + API 用量」类工具；若为上述之一或同类扩展，结论同上：**能查看用量/模型信息，不能自动写入迭代日志**。

**结论（直接回答）**：  
这三类插件**可以用于「查看」Auto 模式下的模型使用信息**（尤其是 Cursor Usage Monitor 的 Activity 列表里「每条请求的 model」），前提是 Cursor 用量 API 在 Auto 时也返回实际模型名。它们**不能**直接用于「每次 Agent 执行并记录日志时自动获取并写入」；若要与迭代日志联动，需配合**方案 A**：用插件看到最近一次模型后，手动写入约定文件，或使用能「把最近一次 model 写入 .cursor/current-model-for-iteration-log.txt」的自建扩展/脚本（可参考 Cursor Usage Monitor 调用的 API 自行实现）。
