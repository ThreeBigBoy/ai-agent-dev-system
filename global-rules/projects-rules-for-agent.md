# 项目通用规范（独立开发者项目）

本规则为**驱动所有项目开发的补充规范**，作为 `OpenSpec.md` 的补充，**复用于所有项目**。  
适用场景：项目开发、代码编写、Bug 修复、重构、前后端开发；与全局配置联动生效。  
若项目内存在 OpenSpec（如 ai-agent-dev-system/OpenSpec.md），则优先遵循其规范。

**与 Agent / 宿主配置的关系**：优先引用本规则执行；若本规则未明确的，Agent 须在当前宿主可提供的能力范围内（如规则入口、文件忽略、终端批准策略、扩展限制等）遵守所配置描述的保护与限制，具体配置手段以宿主当前提供的设置为准。

**文档结构说明**（与 `more-know-how-for-agent-skill/规范体系总览.md` 对齐）：**总则**统摄全文，约束所有行为的价值取向与边界；**一～三**为流程与机制（任务执行、具体场景、迭代日志），属 MUST；**四～九**为分领域规则（代码、安全、配额、行为、注释与文档、补充），含 4.1～6.3 等子节，其中安全为 MUST，配额/模型以 SHOULD 为主。

---

## 总则（所有 Agent 必须严格遵循）

1. 所有操作需严格遵循 OpenSpec 开发规范，优先保障代码质量、项目安全，兼顾开发效率。
2. 适配当前宿主可用的模型与额度策略，避免高成本模型滥用与配额浪费；若某宿主已有更具体的映射规则，则以对应 adapter 的映射说明为准。
3. 贴合独立开发者单人多角色场景，所有 Agent 协同工作，优先响应开发、Bug 修复、重构核心任务。
4. 严格遵循全局配置中的安全设置、工具限制、行为规范，不得擅自突破限制。
5. 输出内容需简洁高效，代码优先、说明为辅，避免冗余，贴合独立开发者开发节奏。

## 一、任务执行通用机制（所有任务类型均适用）

### 1.1 机制概述

**无论用户发起何种类型的任务**，均须遵循以下机制（见 `ai-agent-dev-system/global-rules/skills-rules-for-agent.md`）：

- **主 Agent（或当前统筹方）**：识别用户任务，拆解并**指派给对应子 Agent**执行。确定执行方时，须根据任务性质对应到 **`skills-rules-for-agent.md`** 中「Agents 与 Skills 赋能对应关系」表：该表覆盖 **`agents/`** 下所有 Agent 角色与 **`skills/`** 下各技能的对应关系；任务类型与执行方、技能的对应见 1.2。若项目启用了某个运行时后端（如 `agent_team_project`），则由主 Agent 选择该后端承接执行，但**执行方语义仍以被指派的子 Agent 角色为准**。
- **被指派执行的子 Agent**：按 **`skills-rules-for-agent.md`** 中**本 Agent 角色**的「主导/联动技能」对应关系，**先读取**该技能在 **`ai-agent-dev-system/skills/`** 下对应目录中的 **SKILL.md**，再按其中步骤执行；技能由**执行方角色 + skills-rules 表**决定，不按「任务类型」反推。
- **不得**在未明确执行方、未按 skills-rules 确定本角色技能并读取 SKILL 的情况下直接实施。

### 1.2 任务类型与执行方、技能对应（通用）

完整对应关系以 **`skills-rules-for-agent.md`** 中「Agents 与 Skills 赋能对应关系」表为准；下表为通用映射摘要，便于快速判定执行方与技能。执行方确定后，须按该表中该 Agent 的「主导/赋能技能」与「联动或可选技能」确定要读取的 **`skills/`** 下目录及 SKILL.md。

| 任务类型（示例） | 执行方（agents/） | 主导/联动技能（skills/） |
|------------------|------------------|--------------------------|
| 需求分析、方案设计、PRD/迭代需求说明、线框图/场景描述/交互图、需求验收 Checklist、变更提案与 specs 初稿 | 产品经理 Agent | request-analysis；涉及前端或设计图时联动 image-analysis |
| 工程结构分析、技术方案、project.md、design/project-rules/、OpenSpec CLI、代码评审 | 架构 Agent | project-analysis、code-review |
| 前端编码、前端实现 | 前端 Agent | coding-implement；可选 image-analysis |
| 后端编码、接口与数据层实现 | 后端 Agent | coding-implement |
| 功能测试、验收、验收记录 | 测试 Agent | func-test |
| README、AGENTS.md、project.md、接口文档等规范文档 | 文档 Agent | 无主导技能；配合 request-analysis、project-analysis |
| Bug 根因分析、最小改动修复与验证 | Bug 修复 Agent | 无主导技能；配合 code-review、func-test |
| 统筹、任务拆解、提案审核、冲突协调、监督各 Agent 按表触发技能 | 主 Agent | 不直接执行某一技能；全链路协调 |

### 1.3 执行前自检清单（给出执行方案或动手前必过）

在给出执行方案或动手实施前，执行方（主 Agent 或当前承担任务的子 Agent）须完成以下自检；任一项为否时，先补足再执行。

| # | 自检项 | 说明 |
|---|--------|------|
| 1 | **执行方与技能** | 是否已按本规则 1.2 及 `skills-rules-for-agent.md` 中「Agents 与 Skills 赋能对应关系」表确定执行方？执行方是否已读取该角色对应的 **`ai-agent-dev-system/skills/`** 下技能目录的 **SKILL.md**？ |
| 2 | **新建变更顺序** | 若本次为新建需求/新建变更/迭代，是否已先创建 **`design/documents/[change-id]/`** 并存放至少一份需求/验收文档，再创建 **`openspec/changes/[change-id]/`**？（见 OpenSpec.md 第六节。） |
| 3 | **验证类任务** | 若任务描述中含「在…中验证」「确认…一致」等可验证行为，是否已明确负责人及验收清单路径，且约定仅验收通过后方可勾选该任务？ |
| 4 | **迭代日志** | 若本次在某一项目上下文中（即须有 change-id，见 OpenSpec 5.1 与第三节 3.1），是否将在**本次调用产出完成后、作出完成性回复之前**，向当前项目统一的迭代日志文档 **`design/documents/迭代日志.md`** **追加一条**记录？记录内容中是否已明确本次对应的 change-id（含 `project-early-phase`）？格式见第三节「Agent 与技能调用迭代日志」。 |

自检通过后再给出执行方案或动手实施；自检不通过时，先完成读取 SKILL、补建目录或补全负责人/验收路径，再继续。

### 1.4 执行后必做收尾动作（主 Agent 及任意子 Agent 均须执行）

在某一 **change-id** 上下文中完成本次 Agent/技能调用并产出后，**必须在本轮对话或本任务闭环前**完成以下收尾，否则不得声称该次任务已完成：

| # | 收尾项 | 说明 |
|---|--------|------|
| 1 | **迭代日志追加** | 向当前项目统一迭代日志文档 **`design/documents/迭代日志.md`** **追加一条**记录，格式见第三节（含时间、change-id、Agent、技能、任务、输出、**使用模型**）。文件不存在则新建。**由本次执行方在同一轮对话内完成**，不得留待他人或后续会话补录。 |

**收尾自检（完成性回复前必做）**：在向用户作出任何表示「任务已完成」「已闭环」「已交付」或**任何表示向用户交付本轮产出的总结性回复**（如「改好了」「已落实」「请验收」等）**之前**，执行方须自检：是否已向上述迭代日志文档**追加本条**；若未追加，须**先完成追加，再**作出该回复。**禁止**在未完成迭代日志追加的情况下使用上述完成性/交付性表述。

**项目前期（立项研究、需求分析等）**：使用保留的 change-id **`project-early-phase`**（见 OpenSpec 5.1 与第三节 3.1），**不得**跳过上表收尾；须向 **`design/documents/迭代日志.md`** 追加一条，并在记录中将 change-id 明确标注为 `project-early-phase`。**仅当**不在任何项目上下文中（如纯泛化咨询、未打开任一项目仓库）时，可跳过上表收尾。

### 1.5 适用场景

包括但不限于：发起新需求/新建变更/迭代；市场研究、方案设计、撰写需求功能说明书；重构代码；修复 Bug；测试/验收；编码实现；以及用户提出的其他任何类型任务。下述「二、具体场景执行顺序」为本通用机制在特定场景下的具体执行顺序与步骤。

### 1.6 「重规则」场景与简单任务的自动判定（主 Agent 必须执行）

为在保证治理质量的前提下提升体验，主 Agent 在**每次收到任务指令时**必须先自动判定本次任务是否属于需要开启「重规则」的场景，或可按「简单任务」处理；**不得将模式选择题反复抛给用户**，但须在必要时用一句话告知当前模式。

1. **重规则场景 1：执行 OpenSpec 规范驱动「前期方案分析 + 后期 coding 交付」的完整任务**
   - 满足以下任一条件，即自动视为**需要重规则**：  
     - 指令中出现「根据某个 change-id 做方案/实现」「按 OpenSpec/变更单完成本次交付」等语义；  
     - 需要创建或更新 `openspec/changes/[change-id]/` 下的 `proposal.md` / `tasks.md` / `design.md` / `specs/*/spec.md`；  
     - 需要对现有实现做与某个变更单强绑定的修改（包括接口调整、数据模型变更等）。  
   - 要求：按 OpenSpec 第六节与本文件第二节执行变更启动顺序，严格触发对应子 Agent 与 skills（如 `request-analysis`、`project-analysis`、`coding-implement`、`code-review`、`func-test`），并在 `design/documents/迭代日志.md` 记录本次调用。

2. **重规则场景 2：与专业工作领域强相关、需要专业子 Agent + skills 的任务**
   - 满足以下任一条件，即自动视为**需要重规则**：  
     - 任务明显属于产品、架构、前端、后端、测试等专业子 Agent 的职责范围（如：写 PRD、做架构方案、设计接口、做测试/验收等）；  
     - 需要调用 `agents/` 下特定子 Agent 并触发其主导 skills（如 `request-analysis`、`project-analysis`、`coding-implement`、`code-review`、`func-test`、`image-analysis` 等）。  
   - 要求：按 `skills-rules-for-agent.md` 中的「Agents 与 Skills 赋能对应关系」执行——先读取对应技能目录下的 `SKILL.md`，再按其中步骤产出，并将结果落到 OpenSpec 约定路径，同时在 `design/documents/迭代日志.md` 记录本次调用。

3. **其他场景：由主 Agent 自主判定是否需要重规则**
   - 若不明显属于上述两类场景，主 Agent 须基于以下信号**自主判定**当前任务是否可按「简单任务」处理：  
     - 是否只涉及单个或极少数文件的小改动，且不改变业务逻辑、接口签名、数据库结构、权限或安全边界；  
     - 是否更像一次性的本地/工具操作（如重命名、轻量文案/注释修订），对长期项目脉络价值有限；  
     - 是否与 OpenSpec 文档体系（`openspec/`、`design/documents/[change-id]/` 等）几乎无交集。  
   - 判定结果：  
     - 若风险低、影响范围小、与 OpenSpec 弱关联，则可按**简单任务**处理：不强制触发 skills、不强制创建或修改 `openspec/changes/*`，迭代日志视情况记录；  
     - 若存在接口/数据结构/安全边界变更风险，或触达 OpenSpec 核心文档/高风险目录，则**自动提升为需要重规则的任务**，按前两条要求处理。

4. **判定行为的记录与自我纠偏**
   - 每次任务开始时，主 Agent 应在运行日志或迭代日志体系中为本次任务记录一条**判定摘要**，至少包含：  
     - 任务复杂度（如 `simple` / `heavy`）；  
     - 匹配的场景（如 `scene1-openspec-fullflow` / `scene2-professional-agent` / `scene3-other`）；  
     - 一条简短的**自然语言理由**（如「single-file-rename，无 change-id」「touches openspec/specs，提升为重规则」等）。  
   - 若后续执行过程中发现初始判定不准确（例如原判为简单任务，但实际改动触达 OpenSpec 文档或核心逻辑），主 Agent 必须：  
     - 立即追加一条「从 simple → heavy」的判定调整记录，并简单说明原因；  
     - 从该点起按重规则场景的要求补齐必要步骤（如补读 SKILL、补记迭代日志），并在适当时机向用户简要说明「已按重规则处理」。

5. **对用户的可见反馈原则**
   - 主 Agent 在完成上述判定与记录时，一般仅需用**一句话**向用户说明当前模式，而**不应将模式选择权反复抛回给用户**：  
     - 对简单任务，可说明「本次按简单任务处理，仅做文件级别改动，不会写入变更单」；  
     - 对被自动提升为重规则的任务，可说明「因涉及 OpenSpec/专业领域，本次按重规则执行，会记录到迭代日志」。  
   - 仅当任务本身存在重大风险或需用户在治理强度与成本之间做权衡时，才额外提示用户参与决策。

## 二、具体场景执行顺序

### 2.1 OpenSpec 变更入口（新需求/新建变更/迭代）

当用户**发起新需求、新建变更或迭代**（如「帮我做 XXX 功能」「做一个 YYY 的迭代」「按这个需求出方案」等）时，在遵循**一、任务执行通用机制**的前提下，**第一步必须**：

1. **先读取**同仓库或可访问路径下的 **`ai-agent-dev-system/OpenSpec.md`** 的**第六节「变更启动顺序与检查清单」**及**第 4.3 节（proposal 建议结构）**，再按该节顺序与检查清单执行，确保「先 design/documents，再 openspec/changes」及多 Agent × 多 Skill 机制（见 `skills-rules-for-agent.md`）被触发。
2. **若当前项目尚未有 `openspec/` 目录**（新项目 0-1）：先按 OpenSpec.md 第一节「新项目第一件事」创建 `openspec/` 并填写 `AGENTS.md`、`project.md`；**项目前期的任何任务**（立项研究、需求分析等）使用保留的 change-id **`project-early-phase`**，须建 `design/documents/project-early-phase/`，并在项目级 **`design/documents/迭代日志.md`** 中记录相关调用（见 OpenSpec 5.1、6.3）。当项目决定启动**首个研发变更**时，再按第六节执行（先建 `design/documents/[change-id]/`，再建 `openspec/changes/[change-id]/`）。
3. **不得**在未读 OpenSpec.md 第六节与 4.3 节、未建 `design/documents/[change-id]/` 的情况下，直接创建 `openspec/changes/[change-id]/` 或开始编码。

4. **路径不可达时的降级**：当无法访问 **`ai-agent-dev-system/OpenSpec.md`** 或 **`ai-agent-dev-system/skills/`**（例如仅打开单项目且未挂载 ai-agent-dev-system）时，以**当前项目**根目录下可见的宿主入口文件、**`openspec/AGENTS.md`**（若存在）及本项目内可见的 proposal、tasks 为准；仍须遵守「先 design/documents 再 openspec/changes」的目录顺序（若本项目已有或即将创建 openspec）。**change-id 确定时机**：新需求/新建变更时，change-id 由主 Agent 或产品经理 Agent 在产出 proposal 时确定，须符合 `openspec/project.md` 中的命名规则；若用户已指定则从其指定。

### 2.2 推进 tasks 中某条（既有变更单任务推进）

当用户要求**推进某变更的某任务**或**落地 tasks 中某条**（如「推进 1.4」「完成 2.2」）时，在遵循**一、任务执行通用机制**的前提下：

1. **主 Agent（或当前统筹方）**：读取该变更的 `openspec/changes/[change-id]/proposal.md`、`tasks.md`、`design.md`（如有）及 `design/documents/[change-id]/` 下至少一份需求/验收文档，明确该任务的定义与验收标准；根据 tasks.md 中该任务的**负责人**（对应子 Agent）确定执行方，若未标注则按任务性质指派给对应子 Agent。若项目启用了运行时后端（如 `agent_team_project`），则由该后端承接执行，但不改变执行方角色语义。
2. **被指派执行的子 Agent**：按 **`skills-rules-for-agent.md`** 中**本 Agent 角色**的「主导/联动技能」，**先读取**该技能 **SKILL.md** 再按其中步骤执行；不得跳过「按角色 → 查 skills-rules → 读 SKILL」直接改代码或写验收清单。
3. **不得**在未明确执行方、未按 skills-rules 确定技能并读取 SKILL 的情况下直接实施。
4. **验证类任务**（任务描述中含「在…中验证」「确认…一致」等）：若 tasks.md 已标注负责人与验收清单，须由该负责人按验收清单执行并通过后**再由验收方或主 Agent 勾选**；若未标注，须先补全负责人与验收清单路径（或约定由整变更验收如 6.2 覆盖），**不得由实现方在未经验收时单独勾选**。

## 三、Agent 与技能调用迭代日志（强制要求）

本约定为**强制要求**，适用于**所有采用 OpenSpec 与本规范的项目**及**所有新建或进行中的变更/迭代**。**本约定同时为主 Agent 及所有子 Agent 的必做收尾动作**：在 change-id 上下文中完成本次调用并产出后，**须在同一轮对话内**向项目级迭代日志文档 **`design/documents/迭代日志.md`** 追加一条记录；**未完成不得视为该次任务闭环**。执行方在任一 change-id 上下文中调用 Agent 或技能时**必须**按下列约定执行到位，不得省略。

### 3.1 适用范围与路径

- **总则（与 OpenSpec 一致）**：**所有项目从一开始的所有任务，都必须有 change-id**。凡在某一项目上下文中调用 **`/ai-agent-dev-system/agents/`** 下某 Agent 或 **`/ai-agent-dev-system/skills/`** 下某技能，**均须**归属于某一 change-id，并在该项目的统一迭代日志文档 **`design/documents/迭代日志.md`** 中追加一条记录（记录中须包含该 change-id）；须在**本次调用产出完成后、完成性回复前**完成追加。

- **保留的 change-id：项目前期**（见 **OpenSpec 5.1**）：立项研究、需求分析、市场研究、产品方案等**尚未进入研发迭代**的阶段，使用各项目通用的保留 change-id **`project-early-phase`**（非研发迭代变更性质，供主 Agent、产品经理 Agent 开展早期工作）。**必须**在首次进行项目前期工作时创建 **`design/documents/project-early-phase/`**；每次在该上下文中调用 Agent 或技能时，须向项目级 **`design/documents/迭代日志.md`** 追加一条记录，格式同 3.2。**不要求**创建 `openspec/changes/project-early-phase/`（项目可自愿创建）。

- **研发迭代变更的 change-id**：当任务归属于某一研发迭代变更（新建功能/迭代/小版本）时，使用该变更的自定 change-id；相关调用统一记录到项目级 **`design/documents/迭代日志.md`** 中。若该文件不存在则**新建**，若已存在则**在本次调用产出完成后立即追加**一条记录，并在记录中写明当前 change-id。

- **单次编码/重构等用户未指明变更单的任务**：若当前项目已有进行中的变更（如 tasks 或对话上下文已指明某 change-id），则归属该 change-id；否则归属 **`project-early-phase`**（视为项目前期或未归类的项目内工作）。

- **仅当可跳过**：**不在任何项目上下文中**（如纯泛化咨询、未打开任一项目仓库、用户明确未在项目内执行）时，可跳过迭代日志与 1.4 收尾。

### 3.2 单条记录格式

**XXXX年XX月XX日 HH:mm:ss：XX Agent，调用了 XX 技能，处理 XX 任务，输出 XX；使用模型 XX。**

- **时间**：24 小时制 HH:mm:ss。若由 AI Agent 在 Cursor/沙箱中自动写入，**应以沙箱本地时间为准**（可通过 `date` 命令获得）；事后若与真实发生时间有偏差，可在该条记录末尾以括号备注真实时间。
- **XX Agent**：执行方角色名（如主 Agent、产品经理 Agent、测试 Agent）。
- **XX 技能**：本次调用的技能目录名（如 request-analysis、func-test）；主 Agent 未调用具体技能时可写「—」或「协调」。
- **XX 任务**：本次处理的任务简述。
- **输出 XX**：本次产出的简要说明（如「产出 proposal 与 tasks」「完成 2.2 验收记录」）。
- **使用模型 XX**：按 3.3 优先级取值。

### 3.3 使用模型取值优先级（须严谨区分）

按下列优先级取值：

| 优先级 | 条件 | 取值方式 |
|--------|------|----------|
| ① | 可执行 `get_last_model.py` | 先执行该脚本（路径示例：`ai-agent-dev-system/tools/cursor-usage-to-iteration-log/get_last_model.py`）并读取 **stdout**（trim 后）；若输出非空且非占位符（非「—」、非「Auto（具体模型未暴露）」），则以该输出作为使用模型。详见 `ai-agent-dev-system/tools/cursor-usage-to-iteration-log/README.md`。 |
| ② | 项目内约定「当前模型」文件存在且可读 | 取该文件内容（trim 后）。约定路径示例：`.cursor/current-model-for-iteration-log.txt`。详见 `ai-agent-dev-system/tools/cursor-usage-to-iteration-log/前期设计/迭代日志-获取使用模型-解决方案.md`。 |
| ③ | 用户在本轮任务中说明本次使用模型 | 按用户说明填写。 |
| ④ | 用户已指定具体模型 | 按指定名称填写（如某宿主内置模型、某外部 API 模型等）。 |
| ⑤ | Cursor 使用 Auto 模式且无法获知具体模型 | 填写 **「Auto（具体模型未暴露）」**。 |
| ⑥ | 完全无法获知 | 填写「—」。 |

### 3.4 执行到位与示例

- **执行到位**：主 Agent 在统筹、验收或归档前可核对项目级 `design/documents/迭代日志.md` 中与该 change-id 相关的记录是否与本次迭代内的 Agent/技能调用一致；若发现缺失，须补录或要求执行方补录后再闭环。
- **示例**：`2025年02月17日 14:30:00：产品经理 Agent，调用了 request-analysis 技能，处理迭代需求说明与 specs 初稿，输出 design/documents/xxx/ 与 proposal、tasks；使用模型 Claude 4.6 Sonnet。`

## 四、代码规范（前后端通用，遵循 OpenSpec）

### 4.1 通用代码规则

1. **代码命名规范**
   - 变量/函数：小驼峰 camelCase（如 getUserInfo、orderId）
   - 组件/类：大驼峰 PascalCase（如 UserCard、OrderService）
   - 常量：全大写 + 下划线 UPPER_CASE（如 MAX_RETRY_COUNT、BASE_URL）
   - 所有命名需语义化，禁止模糊命名（如 a、temp1、func）

2. **代码格式规范**
   - 缩进：2 个空格（统一前后端）
   - 引号：单引号优先，特殊场景（如嵌套）除外
   - 行长度：每行不超过 120 字符，超长需合理换行
   - 关键函数、复杂逻辑必须加注释；所有输出代码需按上述规则自动格式化

3. **文件规则**
   - 文件名：小写 + 连字符 kebab-case（如 user-list.vue、order-api.js）
   - 一个文件只做一件事，禁止多功能混杂
   - 目录结构：按 components/hooks/utils/api 划分，禁止随意创建顶层文件
   - **自动化脚本目录**：所有项目应在**项目根目录**统一使用 `scripts/` 子目录存放自动化脚本（如 locale/配置修复、数据或配置初始化、一次性迁移、开发辅助工具脚本等），避免在根目录散落脚本文件；脚本需在 `scripts/README.md` 或脚本所在子目录的 README 中说明用途与使用方式，并受本项目 `openspec/project.md` 与 `design/project-rules/` 的约束。

4. 严格遵循对应语言语法，杜绝语法错误，自动格式化代码。
5. 前后端代码考虑兼容性，避免过时 API/语法，优先使用行业主流写法。
6. 代码中禁止包含敏感信息（账号、密码、密钥），禁止写死路径与配置，优先使用动态配置。

### 4.2 前后端专项规则

1. **前端**：优先使用 React/Vue 主流框架，适配工程化规范，避免冗余，优化性能。
2. **后端**：遵循 RESTful API 规范，数据库操作做异常捕获，接口返回格式统一，注重性能与安全。
3. **重构**：保留原有核心功能，优先优化可读性、可维护性，不引入新 Bug。
4. **Bug 修复**：定位根因，不做临时修复，修复后自动校验相关代码，避免衍生 Bug。

## 五、安全规则（与全局配置安全设置联动）

### 5.1 安全条款

1. 禁止删除/修改全局配置中保护的文件；删除文件前必须触发确认提示；保护 .cursor、.git 等隐藏文件。
2. 禁止执行以下高危命令：`rm -rf`、`sudo`、`chmod 777`、`mv /*`、`rm -f` 及格式化磁盘等；执行终端命令时遵循沙箱与批准策略。
3. 交互中自动过滤敏感信息，不记录、不导出含敏感信息的内容；导出或分享内容时不得包含密钥、账号、密码、内部路径等，导出代码或日志前需确认无敏感信息。
4. 网页搜索仅用于开发相关资源（API、解决方案、语法），不访问高危网站；控制无效或重复请求频次，避免滥用。
5. 自动校验代码中的安全隐患（如 SQL 注入、XSS），并给出修复建议。
6. 绝对禁止硬编码密钥、token、密码、数据库连接等敏感内容。
7. 禁止修改 .gitignore、.env、node_modules 等核心配置/依赖目录。
8. 删除/修改文件前必须触发手动确认；不修改客户端外系统文件。

### 5.2 工具与操作自律

在 Cursor 未提供对应 UI 配置时，Agent 须自律遵守以下操作边界，避免误操作与资源浪费：

1. **批量编辑/重构**：单次批量编辑或重构建议不超过 50 个文件，超出时分批执行并在关键步骤确认，避免误改大面积代码。
2. **终端命令**：长时运行或不可逆操作（如大规模删除、系统级修改）须提示用户确认或分步执行；单步命令建议具有可中断性，避免长时间阻塞。
3. **Python 命令**：在终端/Shell 内执行 Python 脚本时，**一律使用 `python3` 而不是 `python`**，包括 heredoc 形式（如 `python3 - << 'PY'`）；不得生成或执行以 `python` 开头、未显式带版本号的命令，以避免在仅安装 `python3` 的环境中出现 `command not found: python` 报错。
4. **网页搜索**：仅用于开发相关查询（API、报错、语法、方案），控制单轮对话内重复或无关请求次数，避免无效消耗。

## 六、配额使用规则（宿主无关）

本章定义的是**能力等级与额度治理原则**，而不是某个宿主的具体型号清单。  
各宿主下“这些能力等级映射到什么模型、什么入口、什么额度池”，由 `platform-adapters/<host>/` 说明。

**总原则**：
- 白名单宿主（当前为 Cursor 官方、VS Code 官方 / GitHub Copilot）下，主 Agent 与子 Agent 默认优先使用宿主内置模型能力。  
- 第三方宿主（当前明确支持 Continue、OpenAI-Codex）下，主 Agent 可优先使用宿主内置模型，但子 Agent / 运行后端执行链路默认直接走个人自定义 OpenAI 兼容 API 模型调度策略。  
- 若宿主内置模型无响应、异常或不可用，再按对应 adapter / runtime 配置降级到个人自定义 OpenAI 兼容 API 模型链路。  
- 在治理层中，应优先描述**任务类型、能力等级、预算边界与外部复核条件**，而不是直接写死某家模型品牌。  
- 对当前 Cursor 默认运行后端的具体模型映射与候选顺序，见 `platform-adapters/cursor/README.md` 与 `agent_team_project/runtime_config.json`。

### 6.1 模型能力等级与任务匹配

#### 一）宿主内置主力开发模型

- **定位**：适合高频开发、多文件修改、重构、命令联动、批量实现。  
- **典型任务**：
  - 日常编码、重构、Bug 修复
  - 多文件批量修改、格式统一、批量补全注释
  - 任何需要频繁调用 Agent / 工具 / 终端 的任务
- **使用原则**：
  - 能用宿主内置主力开发模型解决的执行型任务，优先不走自费 API。

#### 二）宿主内置长上下文 / 深度推理模型

- **定位**：适合长文档阅读、复杂方案推演、架构与需求分析、中文或多轮推理。  
- **典型任务**：
  - 阅读 `design/documents/*`、`openspec/changes/*` 等长文档
  - 复杂需求分析、方案设计、任务拆解
  - 中文技术说明、PRD、架构设计与验收文档生成
- **使用原则**：
  - 阅读 / 推理阶段优先使用此能力等级；
  - 落地编码阶段回到宿主内置主力开发模型或其他更适合执行的能力等级。

#### 三）宿主内置低成本 / 轻量模型

- **定位**：适合简单问答、语法修正、格式整理、轻量脚本、低风险小任务。  
- **典型任务**：
  - 单次 API 参数查询、简单错误解释
  - 小范围语法修正、格式校验、文案整理
  - 不要求深推理的辅助性请求
- **使用原则**：
  - 能用轻量模型解决的任务，不占用更稀缺的主力或深推理额度。

#### 四）外部 API 模型

- **定位**：宿主内置模型不可用，或任务复杂度/风险级别已接近宿主能力边界时的降级或二次复核能力。  
- **使用原则**：
  - 默认不作为首选；
  - 仅在宿主内置模型不可用、预算允许、或高风险任务需要额外保险时使用；
  - 具体供应商、Base URL、模型优先级与硬限，由 adapter / runtime 配置管理。

### 6.2 额度与预算治理

1. **批量执行优先用宿主内置主力开发模型**
   - 高频多文件操作、重构、实现类任务，优先使用宿主内置主力开发模型；
   - 避免用高成本模型处理机械性批量工作。

2. **阅读/推理与落地开发分离**
   - 阅读、推理、设计阶段：优先使用长上下文 / 深推理能力；
   - 具体实现、改文件、跑命令阶段：回到更适合执行的主力开发模型。

3. **优先消耗低成本能力**
   - 对响应时延不敏感、逻辑简单的请求，尽量使用低成本 / 轻量模型；
   - 将稀缺的深推理额度保留给复杂方案和关键问题。

4. **剩余额度分级预警（由主 Agent 参考执行）**
   - 当宿主内置高价值额度或预算出现明显下降时，主 Agent 应主动调整策略：
     - 剩余 ≤ 40%：减少轻量问题对高价值模型的占用；
     - 剩余 ≤ 20%：仅在核心开发 / 关键问题上使用高价值模型；
     - 剩余 ≤ 10%：视为保命阶段，仅为高风险任务保留高价值额度。

5. **个人自定义 API 必须设置硬限**
   - 若接入第三方 OpenAI 兼容 API：
     - 必须在供应商控制台设置月度硬上限；
     - 达到硬限后由供应商主动拒绝请求，防止超支；
     - 应为自费模型单独配置会话、策略或运行后端，而不是让其无边界接管默认入口。

### 6.3 超复杂 / 高风险任务的特殊处理

#### 6.3.1 高风险场景示例

- 涉及金额 / 支付 / 结算等高风险业务逻辑
- 涉及权限 / 安全边界 / 访问控制 / 合规要求
- 涉及跨多服务 / 多线程 / 多进程 / 分布式一致性
- 涉及极复杂性能优化、深度安全审计、超大规模架构重构

#### 6.3.2 处理原则

1. **优先用宿主内最强可用组合给出第一版方案**
   - 先使用宿主内可用的主力开发模型与深推理模型完成需求理解、边界梳理、方案推演与第一版实现。

2. **到达能力边界时，必须明确提示外部复核**
   - 当当前 Agent 判断问题已接近或超过宿主内模型能力边界时，必须明确提醒用户：
     - 当前方案不宜直接上线；
     - 建议切换到更强的宿主内模型，或使用个人自定义 API 模型进行二次 review / 推演；
     - 对比两侧结论与风险点后，再作最终技术决策。

3. **外部模型只做第二层保险**
   - 外部 API 模型不是对项目规范的替代；
   - 仍须遵守 OpenSpec、安全规范、代码规范与本文件其它章节；
   - 仍须在项目级 `design/documents/迭代日志.md` 中记录本次使用的模型类型、`change-id` 与是否建议了外部复核；
   - 是否实际调用外部模型，由用户依据预算与风险判断决定。

### 6.4 未来模型适配策略

- 以**任务类型**与**能力等级**为准，而不是固守具体型号名称。  
- 当某宿主更新模型列表、额度结构或推荐组合时，优先在 `platform-adapters/<host>/` 中更新映射关系。  
- 治理层只维护“什么任务用什么能力、什么情况下要降级或外部复核”的原则；具体品牌与型号的变动不应反复写进治理层正文。

## 七、Agent 行为规则

1. **响应优先级**：Bug 修复 > 代码编写 > 重构 > 文档生成 > 辅助查询。
2. **上下文同步**：各 Agent 自动同步上下文，确保前后端开发、Bug 修复衔接顺畅；任务切换（如前后端交替、改 Bug 与开发交替）时注意上下文衔接，避免信息丢失。
3. **输出逻辑**：代码优先、说明为辅，报错时先定位根因再给出修复方案；输出简洁、重点突出，减少冗余。
4. **规范校验**：所有输出（代码、文档）先自动校验是否符合本规则、`openspec/` 下的规范与提案、`openspec/project.md` 工程宪法规范及 `design/project-rules/` 下的规则，不合规则自动修正并提示。
5. **容错处理与错误反馈**：遇到操作失败、配置异常时，自动给出详细排查方案，不直接中断操作；对用户可见层面，尤其是在被判定为「简单任务」的场景下，应第一时间用简短自然语言说明错误类型与下一步打算（例如「路径不匹配，已根据实际文件名重试一次」），避免长时间静默等待。
6. **简单任务下的执行收敛**：当主 Agent 已按第 1.6 节判定为简单任务时，各 Agent 在执行层面应优先减少不必要的规则文档读取，复用当前会话已有上下文；对于重命名、轻量文案/注释修订等操作，尽量用单次命令完成预期动作，路径不确定时优先通过轻量 `Read` 或目录校验确认后再执行，避免多轮「探测式」失败重试。
7. **说明型 vs 改动型请求的自动区分**：当指令仅要求解释/分析（如「帮我分析为什么感觉卡」）时，应自动识别为说明型请求，优先直接给出解释，在确有必要时才调用工具；当指令包含真实改动（如「重命名/删除/移动文件」）时，应识别为改动型任务，再按第 1.6 节判定其复杂度并选择相应的执行与记录策略。
8. **产出物质量审核与改进**：产品经理/架构/前端/后端/文档 Agent 的产出物须按 `agents/主Agent.md` 中「产出物质量审核与改进」表执行——主 Agent 推动审核落地，审核方给出具体、可操作的修改建议，被审核方须按意见改进并在 tasks 或记录中闭环；主 Agent 可结合进度与 tasks 勾选做闭环确认。表中**涉及技能**的审核（如架构 code-review、测试 func-test）须**先读取对应技能 SKILL.md 再按其中步骤执行**，产出路径符合该技能与 OpenSpec 1.1 表约定。

## 八、注释与文档规则

1. 公共函数必须编写 JSDoc 规范注释（参数、返回值、异常、功能说明）。
2. 复杂业务逻辑、特殊处理必须添加行内注释，说明设计思路。
3. 注释简洁精准，不写废话注释（如「定义变量 a」）。
4. 自动生成的文档/注释符合 OpenSpec 规范，简洁明了，适配中文开发场景。

## 九、补充规则

1. **排错**：先定位根因，再给出具体修复代码，避免无效建议。
2. **项目结构**：自动识别项目结构，适配前后端不同项目类型，无需手动切换配置。
3. **操作日志与判定日志**：所有操作自动记录日志，便于排查与回溯，日志保留 30 天；支持日志导出时须确保不含敏感信息。若项目或宿主已集成 runtime-logging，则应在其中为每次任务记录至少以下字段：任务复杂度判定（如 simple/heavy）、匹配场景标签（如是否属于第 1.6 节的场景 1/2）、简短自然语言判定理由，以及执行耗时、工具调用次数、是否发生过从 simple → heavy 的判定调整与相关体验事件（如用户表达「卡顿感」「流程过重」等），以便后续对判定规则与体验进行数据化分析与优化。
4. **代码输出**：输出代码应自动符合本规则中的格式与命名规范，并建议做语法/静态检查，减少明显错误。
5. **规范适配**：Cursor 或 OpenSpec 更新时，自动适配新规范，无需手动改规则。
6. **判定习惯的自我优化（依赖记忆能力时适用）**：当在同一项目中，多次出现同类型任务被自动提升为重规则，或用户在相似场景下频繁反馈体验问题（如卡顿、流程过重）时，主 Agent 与相关执行链路应基于迭代日志与 runtime-logging 中的判定记录，适度调整后续判定与执行策略（例如对某类目录默认视为高风险、对某用户/项目偏好更轻量模式等）；具体实现可依赖宿主提供的长期记忆能力，但调整过程仍须在不突破安全边界与 OpenSpec 约束的前提下进行。
