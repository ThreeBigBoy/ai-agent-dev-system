## 一、整体结构：一套四层「宪法体系」

- **第 0 层：运行时入口（只负责跳转，不定义新规范）**
  - **全局入口（Workspace 级）**：
    - 目录：`ai-agent-dev-system/.cursor/rules/`
    - 典型文件：
      - `agent.mdc`：定义「主 Agent」身份、职责，以及必须遵循 OpenSpec 与 `global-rules/`；在 Cursor 规则系统中，作为**所有对话的顶层行为/身份入口**。
      - `global-rules.mdc`：强制要求「对话第一条消息时，必须先读取 `global-rules/projects-rules-for-agent.md` 与 `global-rules/skills-rules-for-agent.md`，并据此判定执行方与技能」；在 Cursor 中将这些全局规范**挂载为始终生效的 workspace 规则源**。
    - **定位**：把 `OpenSpec.md` + `global-rules/*.md` + `agents/` + `skills/` 整套规范「装载」进 **Cursor** 的规则系统，是**Cursor 宿主**下的全局入口层（V2.2 起强调：治理内核宿主无关，入口文件按宿主各归其位）。
  - **项目入口（单项目 runtime 门卫）**：
    - **定位**：项目级 `specLevel: runtime-config`，只管「在该项目中，先读哪几份真正的规范」，不另起规范正文。
    - **说明（V2.2 多宿主）**：不同宿主的入口文件位置不同，本层只强调“入口壳”职责，不把某一宿主写死为唯一入口：
      - Cursor：项目根可使用 `.cursorrules` 作为入口壳（若团队仍采用该机制）。
      - VS Code 官方 / GitHub Copilot：根 `AGENTS.md`、`.github/agents/*.agent.md` 作为入口壳。
      - 第三方宿主：按 `platform-adapters/generic/*` 中对应宿主说明设置入口壳与运行触发。
    - **入口壳应做的事（所有宿主共通）**：
      - 指明所有任务走「主 Agent 拆任务 → 按 `skills-rules-for-agent.md` 查角色技能 → 先读对应 SKILL 再执行」。
      - 新需求 / 新变更时，**跳转**到 `ai-agent-dev-system/OpenSpec.md` 的 §6（变更启动顺序）+ §4.3（proposal 结构），不在入口壳重复细节。
      - 若访问不到 `ai-agent-dev-system`，则退回本项目 `openspec/AGENTS.md` 的要点版入口（先 `design/documents` 再 `openspec/changes`）。
      - 若项目启用默认运行后端 `agent_team_project/`：决策/反馈文件命名以 **`agent_decision.json`**、**`agent_feedback.txt`** 为主。

### 补充：V2.2 四层架构（与 README.md 对齐）

V2.2 将整体体系按「治理 → 适配 → 入口 → 运行」拆为四层，便于跨宿主复用与边界收敛（见仓库根 `README.md` 的同名章节思想）：

1. **治理内核层（宿主无关）**
   - **文件**：`OpenSpec.md`、`global-rules/*.md`、`agents/*.md`、`skills/*/SKILL.md`
   - **职责**：定义 change-id、变更启动顺序、角色边界、技能触发、日志制度、审核与闭环规则（“怎么办”）。

2. **宿主适配层（platform-adapters/*）**
   - **目录**：`platform-adapters/cursor/*`、`platform-adapters/vscode/*`、`platform-adapters/generic/*`
   - **职责**：说明不同宿主如何加载规则、如何接线 MCP/扩展、如何落地 `decision_sink / runtime_trigger / feedback_bridge / workspace_binding`（“各宿主怎么接线”）。

3. **宿主入口层（各宿主要求的位置）**
   - **示例**：
     - Cursor：`.cursor/rules/*.mdc`（workspace 规则入口壳），可选 `.cursorrules`（项目入口壳）
     - VS Code：根 `AGENTS.md`、`.github/agents/*.agent.md`
   - **职责**：作为宿主可直接发现/加载的「最薄入口壳」，只做跳转与约束声明，不堆叠厚制度正文。

4. **运行后端层（可插拔实现）**
   - **当前默认实现**：`agent_team_project/`
   - **职责**：承接决策写入、执行、反馈与状态持久化；不得改写治理层规则与角色边界（“按决策执行”）。

一句话：**治理内核定义规则；适配层定义接线；入口层负责装载；运行后端负责执行。**

## 二、全局层：所有项目共享的「总宪法 + 补充宪法」

- **核心宪法（唯一源头）**
  - 文件：`ai-agent-dev-system/OpenSpec.md`（core）
  - **以 MUST 为主**：
    - 文档定位与目录结构（`openspec/`、`design/documents/` 等）。
    - 变更模型：specs / changes / archive。
    - §4.3：`proposal.md` 建议结构。
    - §6：变更启动顺序与 5 条检查清单（先 `design/documents/[change-id]/` 再 `openspec/changes/[change-id]/`，+ 迭代日志等）。

- **全局补充宪法**
  - 文件：`ai-agent-dev-system/global-rules/projects-rules-for-agent.md`
    - **总则**（5 条）：统摄全文，约束所有行为的价值取向与边界（遵循 OpenSpec、配额、协同、全局配置、简洁输出）；不参与「一～九」编号，位于正文流程与分领域规则之前。
    - MUST：
      - 「任务执行通用机制」：先定执行方（Agent），再按 `skills-rules` 定技能并读 SKILL，禁止跳过。
      - 「OpenSpec 变更入口」：新变更必须先读 OpenSpec §6 + §4.3。
      - 迭代日志机制：所有任务自项目一开始均须有 change-id；项目前期（立项研究、需求分析等）使用保留的 **`project-early-phase`**（见 OpenSpec 5.1），统一在项目级 `design/documents/迭代日志.md` 中强制记录 Agent + Skill 调用，并在记录内写明当前 change-id。
      - 安全规则：禁止高危命令、敏感信息、误删等。
    - SHOULD：
      - 模型/配额使用策略、效率类建议。

  - 文件：`ai-agent-dev-system/global-rules/skills-rules-for-agent.md`
    - MUST：
      - 定义各 Agent 角色的主导/联动技能（request-analysis、project-analysis、coding-implement、code-review、func-test、image-analysis）。
      - 约定：命中技能场景时，**执行方必须先读对应 `skills/<name>/SKILL.md`**，按其中步骤与 REFERENCE 产出（含路径和最小结构）。
    - SHOULD：
      - 各技能下更细节的流程优化建议。

  - 文件：`ai-agent-dev-system/global-rules/readme-rules-for-agent.md`
    - 多为 README / 文档写作规则，主要是 SHOULD，安全/一致性小部分是 MUST。

## 三、项目层：单项目的「工程宪法 + 宪法补充」

- **项目工程宪法**
  - 文件：`openspec/project.md`（`specLevel: project-constitution`）
  - **对本项目是 MUST**：
    - 项目简介、技术栈、目录角色（例如：仅用 Shopify Liquid、无独立后端、`theme-health-food/` 为主题根）。
    - change-id / capability 命名规则。
    - 明确：`design/project-rules/` 是本宪法的补充约束，实现与评审时**必须与本文件一起遵守**。
    - 新增的「规范层级本项目落地版」小节，统一声明：
      - 全局 MUST：`OpenSpec.md` + `projects-rules` 中关键章节 + `skills-rules` 的矩阵与「先读 SKILL」。
      - 本项目 MUST：本文件 + `design/project-rules/SHOPIFY_THEME_STRUCTURE.md`。
      - 本项目补充规范：哪些是当前阶段 SHOULD，将来（上架 Theme Store）会升级为 MUST。
      - `.cursorrules` 的角色仅是入口，不新增规范。

- **工程宪法补充**
  - 目录：`design/project-rules/` 下 3 份文档，统一标记 `specLevel: project-supplement`：

  - `SHOPIFY_THEME_STRUCTURE.md`
    - 默认 binding: MUST。
    - 对本项目：7 大核心目录结构、校验要点、主题根路径等为**强制约束**，开发与评审必须遵守。

  - `shopify-theme-store-requirements.md`
    - 默认 binding: MIXED。
    - 「执行力说明（本项目）」：
      - MVP/自用阶段：整体作为 Theme Store 审核的**质量上限参考（SHOULD）**。
      - 真正准备上架 Theme Store 时：其中按 Shopify 官方审核文档整理的条款整体视为 MUST，逐条对照验收。

  - `shopify-theme-core-concepts.md`
    - 默认 binding: SHOULD。
    - 0–6 章：核心概念和结构解释 → 知识/建议。
    - 第 7 章「开发实现约束（总结版）」：一组**应优先遵守**的实现规则，用于具体化 Theme 开发的好实践，但前提是不与上层 `OpenSpec`、`global-rules`、`project.md` 冲突。

- **项目 AI 工作说明书**
  - 文件：`openspec/AGENTS.md`
  - 定位：
    - 告诉 AI：项目类型、开发环境、关键路径（`openspec/specs`、`openspec/changes`、`design/project-rules`、`design/documents`）。
    - 列出本项目可用的 Skills、触发词，并显式要求「先读 SKILL，再按步骤执行」。
    - 提醒：变更启动顺序以 `OpenSpec.md` 第 6 节为唯一依据。

## 四、运行流程视角：AI/人类如何用这套体系

- **任何任务**（需求、方案、编码、测试、文档、重构、修 Bug）：
  1. 按「宿主入口壳」/ 全局 Rules，先加载：
     - `OpenSpec.md`（至少 §1、§4.3、§6）。
     - `projects-rules-for-agent.md`（任务执行机制、迭代日志、安全）。
     - `skills-rules-for-agent.md`（角色 ↔ 技能）。
     - 当前项目的 `openspec/project.md` + `design/project-rules/` 中标为 MUST 的文件。
  2. 主 Agent 拆任务 → 确定执行方 Agent；执行方按 `skills-rules` 找到应使用的 SKILL → **先读该 SKILL 的 `SKILL.md`（和 REFERENCE）** → 再实施。
  3. 所有产出（需求文档、spec、design、代码实现、review 记录、验收记录），都按相应 SKILL 规定的「最小结构 + 自检」生成，放在 OpenSpec 规范约定的位置。
  4. 在项目级 `design/documents/迭代日志.md` 中记录本次 Agent + Skill 调用，并在记录中写明对应 change-id（项目前期使用 **`project-early-phase`**）。

- **新建变更 / 迭代**：
  - 入口统一：`OpenSpec.md` §6 + `.cursorrules` / `AGENTS.md` 的提醒：
    - 先建 `design/documents/[change-id]/` 放需求侧文档；
    - 再建 `openspec/changes/[change-id]/` 编写 `proposal.md`（引用前面的文档）、`tasks.md`、`specs/...`。

## 五、一句话总结

- **规范执行力**：通过统一的层级（core / global-supplement / project-constitution / project-supplement / runtime-config）和每份文档的 MUST/SHOULD 标记，锁定「哪一层一定不能违背」。
- **体系简化**：真正有规范内容的只剩少数几个权威源（`OpenSpec.md`、三份 global-rules、本项目的 `project.md` + `design/project-rules`），`.cursorrules` 和 `AGENTS.md` 只做入口与路由，不复制规范。
- **对 AI 友好**：任何任务都要先过「角色 → 技能 → SKILL.md → OpenSpec 目录 & 路径」，保证工作过程合法、输出质量有结构可检。
